## 可复用原则

1. **三层结构是库形态的最小完整集**：第一层（原始资料）+ 第二层（AI 提炼的卡片）+ 第三层（路由表）——缺任一层，库都是"半活"。第一二层是"存什么"，第三层是"AI 怎么自己用上"。外脑第一二层已经齐了（31 条结构化条目 + README 索引），**真正的缺口在第三层**。
2. **路由表是给 AI 看的，不是给人看的**：README 是给人读的总目录（用户/agent 都得读）；路由表是 system prompt 的一部分，**严格按触发词 + 文件路径执行**，触发词要具体到 2-3 个同义词 + 场景词，不能太宽（"投资" → 全库 = 路由失败）。
3. **路由表上限 10-15 条**：再多就重蹈视频里那位老哥的覆辙——"几千个文件十几个领域全挤一个目录，AI 一跑就懵"。**严格砍**：触发频次低的砍、覆盖范围窄的砍、和其他路由重叠的砍；砍不到的不入表。
4. **永远只读 1-2 个文件，**别整箱倒进上下文**：上下文是稀缺资源，CherryStudio 的"知识库全检索"功能要关掉，改用 Read 工具精确读——路由表本身就是为了避免"整箱倒出来翻"的反模式。
5. **"动手前先查"是核心规则的唯一形态**：10 条路由都共用这一句总规则（"你动手之前先回库里看看有没有现成的"），每条路由只是把"现成的"具体化为"哪个文件"。
6. **自动化是设计出来的，不是 AI 变聪明了**：常见错觉是"我用上 AI 知识库，它就自动会查了"——不是的。AI 的"自动"来自三件套：① 触发词精确匹配 ② 路由路径预先定义 ③ 翻车后人工/AI 主动补规矩。**三件套缺任一 = 假自动**。
7. **翻一次车库里多一条规矩**：路由表本身**永远不删不改原文件**，每次翻车（AI 答错 / 漏查 / 查错页）→ 新建一条 `YYYY-MM-DD_路由表迭代_vN.md` 增量记录 → 用 vN 编号保留历史。**这是活库的"自迭代机制"**——对应反脆弱的"压力 → 强化"。
8. **触发词要窄不要宽**：写"用户问量化"太宽（会匹配所有量化问题）；写"用户问回测 / 过拟合 / CPCV / WFO"才精确——4 个同义词 + 都是量化子场景词。**触发词宽 = 路由失败 = AI 假自动**。
9. **人机边界要硬**：AI 不该查的不要让 AI 查（隐私 / 待决事项 / 主观感受类）；AI 该查却没查的必须有人兜底（路由表体检 + 用户反馈）。**是协同不是托管**——AI 跑的跑、人类审的审。
10. **路由表不能凭空加**：只能由"实际问过的问题"触发新增（用户问过但 AI 没查 = 漏路由），或由"AI 查错页"触发修改。**AI 自己拍脑袋加的路由不算数**——这违反"自动化是设计出来的"原则。
11. **CherryStudio 的 RAG 全检索是反模式**：默认行为是"用户提问时全库向量检索"——这对小型库尚可，对 30+ 条以上的库会噪声淹没信号。**路由表 + Read 工具精确读** 是替代方案，比 RAG 更可控、可解释、可调试。
12. **每月一次"路由表体检"**：固定检查 4 项——① 哪些路由 30 天内 0 触发（砍）② 哪些问题被问过但没路由（补）③ 哪些路由查错页（改触发词）④ 路由表总条数是否在 10-15 区间（多了砍、少了补）。**不体检 = 路由表腐烂**。
13. **路由表自身可以入外脑**：每次"路由表迭代"沉淀一条新条目（增量更新，不动原文），长期下来路由表的历史就是外脑的一条支线——"AI 协作方法论"主题。这条本身就是这个机制的第一个实例。
14. **不要把路由表当万能药**：路由表解决的是"AI 该查但没查"的 80% 场景，剩下 20%（跨路由的复杂问题、需要多步推理的、新领域探索）靠**对话中动态发现**——AI 在对话里发现"这条本该有路由"→ 当场补一条临时路由 → 事后归档。**路由表是基础设施，不是天花板**。
15. **库是 AI 的"代码库"，不是给人看的笔记**：视频里卡巴西的话："你的笔记库是 AI 的代码库；代码库的意义从来不是存着好看，是被跑起来。"——这条原则决定路由表的设计哲学：**不是给人读的清单，是给 AI 跑的程序**。

## 核心逻辑链

1. **前提**：用户看完《把知识库变成 AI 操作手册》视频后，意识到自己的外脑（`D:\knowledge-base\`，31 条结构化条目）是个"半活库"——第二层做得很扎实（每条严格按"元信息→可复用原则→核心逻辑链→分章笔记→自测"模板写），但第三层（路由表）完全缺失，AI 没有"主动按表查"的机制。
2. **问题链**：没有路由表 → CherryStudio 走默认 RAG 全检索 → 30+ 条库噪声淹没信号 → 用户提问时 AI 全凭印象答（"我应该查哪一页"靠 LLM 自身判断）→ 答对的概率不可控（< 50%）→ 用户觉得"AI 知识库没用" → 库沦为"放着好看"。
3. **机制一（三层结构补齐）**：库 = 原始资料 + 卡片 + 路由表；外脑前两层齐，**只在第三层做最小补丁**（10 条路由 + 系统提示词 + 反馈协议）——这是"半活到全活"的最小开关。
4. **机制二（路由表精确化）**：每条路由 = `触发词（2-3 个同义词 + 场景词）→ 文件路径 → AI 怎么用`。触发词要窄（不是"投资"，而是"回测 / 过拟合 / CPCV / WFO"），文件路径要绝对（不是"读决策清单"，而是"`D:\knowledge-base\思维模型\反脆弱决策清单.md`"）。
5. **机制三（CherryStudio 系统提示词落地）**：把 10 条路由表 + 3 条铁律（先查 / 只读 1-2 篇 / 翻车说下次该查哪页）写进 CherryStudio 的智能体系统提示里。**关掉知识库 RAG 全检索选项**，改用 Read 工具精确读（CherryStudio 支持文件系统 Read 工具时）或精准向量检索（只查命中路由的 1-2 个文件）。
6. **机制四（反馈迭代机制）**：每次对话后 AI 自检 3 件事——① 这次回答是否命中路由？② 漏了哪条本该查的？③ 查的那页真解决问题吗？翻车信号 = 用户问 2 次同样问题 / 用户说"AI 越界" / 用户说"这段之前讲过"。翻车 → 新建 `YYYY-MM-DD_路由表迭代_vN.md` 增量记录，**不动路由表原文件**。
7. **机制五（每月体检）**：固定每月 1 次"路由表体检"——砍 0 触发的、补漏的、改查错页的、控条数。这是活库的"反脆弱维护节奏"，对应反脆弱决策清单的 §5 复盘机制。
8. **机制六（路由表自迭代沉淀）**：路由表的迭代历史本身按外脑条目规范沉淀——`YYYY-MM-DD_路由表迭代_vN.md`（用元信息 → 可复用原则 → 核心逻辑链 → 分章笔记 → 自测模板），长期形成外脑的"AI 协作方法论"支线主题。
9. **结果**：外脑从"半活"补到"全活"——10 条路由覆盖 90% 的常见提问场景、3 条铁律保证不超载、反馈机制让路由表自己长、每月体检让路由表不腐烂。**整套补丁约 30 分钟落地**（写 1 条外脑条目 + 复制 system prompt + 关掉 RAG 全检索）。
10. **行动指引**：① 写本条 `2026-09-06_外脑活库化方案_路由表v0.1.md` → ② 按维护约定更新 README → ③ CherryStudio 复制 system prompt → ④ 跑 5-10 次观察哪些路由灵/不灵 → ⑤ 下次对话出 v0.2 增量补丁。
11. **诚实声明**：本文不直接阅读卡巴西 2026-04 原始博客/推文，所有"三层结构 / 路由表 / 翻一次车库里多一条规矩"的表述基于本地视频 faster-whisper-small 转录（120 段全片）+ 视频方法论的多段交叉验证；CherryStudio 的具体 Read 工具能力基于 CherryStudio 官方文档的常见能力描述（具体配置需以你当前 CherryStudio 版本为准）；外脑的 31 条结构化条目基于 `D:\knowledge-base\README.md` 当前内容。

### 第四章　反馈迭代机制（让库"自己长"）

> **核心原则**（视频里 up 主反复强调）：**翻一次车库里多一条规矩**。对应外脑的具体做法：

#### 4.1 每次对话后自检（AI 必做）

对话结束后，AI 自己问三件事：
1. **这次回答是否命中路由表？**（命中 = 路由设计对了；不命中 = 触发词太宽或漏路由）
2. **漏了哪条本该查的？**（用户问的内容本该有路由但 AI 没查 = 漏路由）
3. **查的那页真解决问题吗？**（查了但用户说"还是不对" = 路由查错了页）

#### 4.2 翻车信号（用户侧观察）

| 信号 | 含义 | 处理 |
| --- | --- | --- |
| 用户问 2 次同样问题 | 路由不准（触发词没匹配上） | 调整触发词（加同义词） |
| 用户说"AI 越界 / 答非所问" | 路由跑偏（查了不该查的页） | 收紧触发词（缩小范围） |
| 用户说"这段之前讲过" | 路由没触发（漏路由） | 新增路由 |
| 用户说"你能不能直接答" | 路由过度（不该查的查了） | 砍路由 / 改路由为"提示而非必查" |

#### 4.3 补规矩流程

每次翻车 → 新建 `思维模型/YYYY-MM-DD_路由表迭代_vN.md` 增量记录，**不动路由表原文件**。迭代文件用外脑条目模板（元信息 → 可复用原则 → 核心逻辑链 → 分章笔记 → 自测），长期形成外脑的"AI 协作方法论"支线主题。

**vN 编号规则**：
- v0.1 = 本条（路由表初始版）
- v0.2 = 第一次迭代（补了 N 条新路由 / 改了 M 条触发词）
- v0.3 = 第二次迭代
- ...
- v1.0 = 路由表稳定后（条数在 10-15 区间，触发词经过 3 个月验证）

### 第七章　验收标准（怎么算"活库起来了"）

> **核心指标**：路由命中 > 80% + 行为可观察 + 路由表迭代有效 + 可解释。

| # | 验收项 | 通过标准 |
| --- | --- | --- |
| 1 | 路由命中率 | 10 个常见问题，AI 至少 8 个主动查对了页（**> 80%**） |
| 2 | 行为可观察 | 一次提问 → AI 先说"我查了 X.md"再回答 |
| 3 | 路由表迭代有效 | 上次答错的，下次问类似问题 AI 会换条路由 |
| 4 | 可解释 | 用户问"为什么查这页"，AI 能说出触发词匹配逻辑 |
| 5 | 反馈机制运转 | 翻车后 AI 主动说"建议新增/修改路由：触发词 X → 查 Y.md" |
| 6 | 体检节奏 | 每月 1 号路由表体检 4 项清单全跑 |

**全部通过 = 活库起来了**。任意一项不通过 → 对应章节的优化方向。
